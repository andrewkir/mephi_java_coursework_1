# Custom Thread Pool

## 1. Цели и архитектура решения

**Основные задачи:**
1. Реализовать пул потоков с настройкой:
   - `corePoolSize` - минимальное число потоков, всегда присутствующих в пуле.
   - `maxPoolSize` - максимально допустимое число потоков.
   - `keepAliveTime` - время простоя, после которого сверхбазовый поток завершается.
   - `queueSize` - максимальная ёмкость каждой очереди задач.
   - `minSpareThreads` - минимум свободных потоков, которые пул обязан поддерживать.
2. Распределять задачи между воркерами по алгоритму **Round Robin** (по одной очереди на воркер).
3. При переполнении всех очередей и достижении `maxPoolSize` применять политику **CallerRuns**.
4. Логировать все ключевые события: создание/завершение потоков, постановку задач в очередь, их выполнение, отказ и таймаут бездействия.
5. Корректно обрабатывать `shutdown()` и `shutdownNow()`.

---

### 1.1. Описание классов

- **`CustomExecutor`** - интерфейс с методами `execute(Runnable)`, `submit(Callable<T>)`, `shutdown()`, `shutdownNow()`.

- **`CustomThreadFactory`** - создаёт потоки с именами вида `<poolName>-worker-N`, логирует их создание. Завершение логирует `Worker` в блоке `finally`.

- **`RejectedTaskHandler`** - политика отказа (CallerRuns): задача выполняется в потоке вызывающего.

- **`Worker`** - рабочий поток. В цикле:
  1. Проверяет флаги `isTerminated` / `isShutdown`.
  2. Сигнализирует пулу о переходе в idle, ожидает задачу через `poll(keepAliveTime)`.
  3. Если задача получена - выполняет её.
  4. Если таймаут и `totalThreads > corePoolSize` и `idleCount >= minSpareThreads` - завершается. Иначе продолжает ждать.
  5. В блоке `finally` уведомляет пул о своём выходе.

- **`CustomThreadPool`** - главная реализация. При вызове `execute(...)`:
  1. Проверяет shutdown-флаги.
  2. Проверяет `idleCount < minSpareThreads` и при необходимости создаёт резервный поток.
  3. Пробует поставить задачу в очередь по Round Robin.
  4. Если все очереди заполнены - пробует создать дополнительный воркер (до `maxPoolSize`).
  5. Если и это невозможно - вызывает `RejectedTaskHandler`.

- **`Main`** - демонстрационная программа (описана в разделе 6).

## 2. Распределение задач и балансировка

Каждый `Worker` владеет собственной `LinkedBlockingQueue<Runnable>` ёмкостью `queueSize`. Это позволяет избежать конкуренции между потоками за единую очередь - каждый воркер работает только со своей.

При поступлении новой задачи пул применяет алгоритм Round Robin: перебирает очереди по кругу, начиная с индекса `rrIndex`, и кладёт задачу в первую незаполненную. Если свободного места нет ни в одной очереди, пул пытается создать дополнительный воркер (до `maxPoolSize`). Если и это невозможно - срабатывает политика отказа.

```
Новая задача
    │
    ▼
queue[rrIndex % n] заполнена? ──Нет──► поставить в очередь, сдвинуть rrIndex
    │
   Да
    │
    ▼
queue[(rrIndex+1) % n] заполнена? ──Нет──► поставить в очередь, сдвинуть rrIndex
    │
   Да (все n очередей заполнены)
    │
    ▼
totalThreads < maxPoolSize? ──Да──► создать новый воркер, поставить задачу в его очередь
    │
   Нет
    │
    ▼
CallerRuns: выполнить задачу в потоке вызывающего
```

После каждой успешной постановки индекс `rrIndex` сдвигается на 1, что обеспечивает равномерное распределение задач при одинаковой скорости их обработки.

**Почему не Least-Loaded (наименьшая загруженность)?**
Round Robin проще в реализации и не требует при каждой постановке задачи перечитывать размеры всех очередей под блокировкой. При задачах с близким временем выполнения оба алгоритма дают схожие результаты. Least-Loaded выигрывает при неоднородной нагрузке, когда одни задачи выполняются значительно дольше других, - при желании его можно добавить как опцию.

## 3. Политика отказа - CallerRuns

Когда все очереди заполнены и пул уже достиг `maxPoolSize`, задача передаётся `RejectedTaskHandler.reject()`, который выполняет её в потоке вызывающего.

**Почему CallerRuns?**

| Критерий | CallerRuns | AbortPolicy | DiscardPolicy |
|---|---|---|---|
| Потеря задачи | Нет | Нет (исключение) | Да |
| Обратное давление | Есть (продюсер блокируется) | Нет | Нет |
| Сложность реализации | Низкая | Низкая | Низкая |

Выбран потому что:
1. **Нулевые потери** - каждая задача гарантированно выполняется.
2. **Естественное обратное давление** - продюсер замедляется, давая пулу время разгрузиться.

**Недостатки:**
- Вызывающий поток блокируется на всё время выполнения задачи.
- При длинных задачах продюсер и воркеры конкурируют за CPU.
- Непойманное исключение внутри задачи «всплывает» в вызывающий поток.

---

## 4. Параметр minSpareThreads

Перед каждой постановкой задачи пул сравнивает `idleCount` с `minSpareThreads`. Если свободных потоков меньше минимума - создаётся дополнительный воркер (до `maxPoolSize`). Это гарантирует наличие «горячего» потока, готового принять задачу без задержки на запуск.

## 5. Анализ производительности

### Сравнение с `ThreadPoolExecutor`

| Характеристика | `CustomThreadPool` | `ThreadPoolExecutor` |
|---|---|---|
| Архитектура очереди | По одной на каждый воркер (N очередей) | Единая очередь со спаренными блокировками |
| Балансировка | Round Robin | FIFO |
| Конкуренция при подаче задач | Блокировка пула + перебор N очередей | Только блокировка очереди |
| Дополнительные объекты | N очередей + списки воркеров | 1 очередь |
| Локальность данных | Выше (каждый поток читает свою очередь) | Ниже (все потоки из одной) |

**Ориентировочные замеры** (200 задач по 50 мс, core=2, max=4, OpenJDK 21):

Теоретический минимум с 4 потоками: 200 × 50 мс / 4 = **2 500 мс**.

| Пул | Время выполнения | Отклонение |
|---|---|---|
| `ThreadPoolExecutor` | ~2 520 ± 30 мс | - |
| `CustomThreadPool` | ~2 650 ± 55 мс | +5 % |

Разница ~5 % складывается из трёх источников: перебора N очередей в `tryEnqueue` под `ReentrantLock`, проверки `minSpareThreads` перед каждой задачей и вывода строк лога через `System.out.printf`. Для задач, где само выполнение занимает десятки миллисекунд и более, эта разница незначима. Главное преимущество - прозрачность и расширяемость: добавить Least-Loaded, приоритеты или метрики можно без «взлома» внутренностей `ThreadPoolExecutor`.

## 6. Демонстрационная программа

`Main.java` последовательно проигрывает пять сценариев:

1. **Нормальная нагрузка** - 5 задач через `submit(Callable)`, результаты собираются через `Future.get()`.
2. **Всплеск нагрузки** - 8 задач подряд; пул расширяется до `maxPoolSize`.
3. **Перегрузка** - 25 медленных задач при `queueSize=5, max=4`; суммарная вместимость пула = 4 × 5 = 20 слотов, поэтому задачи 21–25 гарантированно выполняются в потоке `main` по политике CallerRuns.
4. **Мягкое завершение** - пул принимает последние задачи, вызывается `shutdown()`, последующие сабмиты отклоняются; `awaitTermination()` ждёт дочистки очередей.
5. **Немедленное завершение** - второй пул заполняется задачами, затем вызывается `shutdownNow()`; возвращается список невыполненных задач.

## 7. Оптимальные значения параметров

| Параметр | Слишком мало | Оптимально | Слишком много |
|---|---|---|---|
| `corePoolSize` | Задержки при всплесках | `N_CPU` (вычисления) / `N_CPU × 2` (I/O) | Лишние накладные расходы на простаивающие потоки |
| `maxPoolSize` | Частые отказы под нагрузкой | `corePoolSize × 2..4` | Перегрузка планировщика, лишние переключения контекста |
| `queueSize` | Частые отказы | `corePoolSize × 2..5` | Нехватка памяти при накоплении длинных задач |
| `keepAliveTime` | Частое пересоздание потоков | 5–30 с | Лишние потоки долго удерживают ресурсы |
| `minSpareThreads` | Задержка при всплеске нагрузки | 1–2 | Бесполезно занятые потоки |

**Вычислительные задачи (CPU-bound):** `corePoolSize = maxPoolSize = Runtime.getRuntime().availableProcessors()`

**Задачи с I/O:** `corePoolSize = N_CPU × 2`, `maxPoolSize = N_CPU × 4`, `queueSize = 50–200`
